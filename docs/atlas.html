Map of the tool

Artifact Engine

Modular DFIR triage: it takes Windows and Linux acquisitions, verifies them, extracts them, detects each machine, runs the parsers that apply and leaves a database, a spreadsheet and a report per machine. It runs on Windows; the evidence can be from Windows or from Linux.

One run

Six phases, in this order

phase 0

Integrity

SHA256 of every original that has arrived, into traces.txt, before anything else is touched. Append-only; what was extracted is not an original.

phase 1

Extraction

Nested zip/tar/7z in parallel. Never re-extracts destructively; an acquisition that did not come out whole stays partial in its marker and moves the exit code.

phase 2

Detection

The profiles recognise each machine (KAPE, UAC, Velociraptor, loose folders), its volumes and its VSS snapshots.

phase 3

Parsing

Every parser in one pool ordered by depends_on; one failing does not stop the run, and what an earlier run parsed comes back as cached.

phase 4

Consolidation

<machine>.db, .xlsx and report.txt with log coverage and findings, plus the case's run-summary.

phase 5

Lateral movement

Logon correlation across machines: lateral_movement.csv and an interactive offline graph with pivot chains.

What comes in

Acquisitions it recognises

windows_kape

KAPE / CyLR

Windows acquisition with KAPE/CyLR (KAPE_results/C/... layout)

linux_uac

UAC

Linux acquisition with UAC (looks for uac.log)

windows_liveresponse

Velociraptor LiveResponse

Volatile state. Joined to its host when it arrives inside a KAPE acquisition; on its own it is registered as a machine of its own with a -LR suffix. Built by the detector, not by a profile manifest.

evtx

Loose evtx[-label] folder

Loose Windows event logs dropped in an evtx[-label] folder at the case root (no acquisition around them). The folder becomes its own machine: the whole EVTX toolchain (EvtxECmd per channel, chainsaw, hayabusa) runs over it, the results land in the folder's own .db/.xlsx, and the host feeds the lateral-movement graph like any acquired machine.

weblogs

Loose weblogs[-label] folder

Loose web-server access logs dropped in a weblogs[-label] folder at the case root (no acquisition around them). The folder becomes its own machine: the web parsers run over every file in it and the results land in the folder's own .db/.xlsx.

fortigate

Loose fortigate[-label] folder

Loose FortiGate/FortiOS log export (raw syslog or FortiAnalyzer CSV export) dropped in a fortigate[-label] folder at the case root. The folder becomes its own machine: the fortigate parser builds a flagged timeline that lands in the folder's own .db/.xlsx.

linux_memory

linux_memory

A Linux memory image (.raw/.mem/.vmem/.lime of 64 MB or more, .dmp of 256 MB or more) in the top two levels of the case. Staged like a Windows one (a sibling folder `<stem>_memory/` holding a pointer to the image); when it is staged the image is scanned once for the names a kernel leaves in memory, and an image with a Linux banner and no Windows kernel name gets `memory.linux` (core/memory_os.py), which this profile detects. Volatility 3 runs one linux plugin per parser with the kernel's symbol table from the public ISF index. The image itself is never moved or copied.

windows_memory

windows_memory

A Windows memory image (.raw/.mem/.vmem/.lime of 64 MB or more, .dmp of 256 MB or more) anywhere in the top two levels of the case -- or one whose kernel is unknown; an image recorded as Linux (memory.linux) is taken first by linux_memory. Each image gets a sibling folder `<stem>_memory/` holding a pointer to it, and that folder is the machine: Volatility 3 runs one plugin per parser over the image, the tables land in the folder's own .db/.xlsx, and once the processes' environment has been read the unit is named after the host it names (COMPUTERNAME). The image itself is never moved or copied.

What comes out

The 209 artifacts

One row per parser: where it reads from in the acquisition, what it gets, which folder its tables land in and whether it produces alerts. A table is named after the parser id; a parser driven by an external tool can write several.

Detection

The whole table is findings: rules (Sigma, YARA, GTFOBins) or threat lists (LOLDrivers, LOLRMM, LOLBAS, ransomware).

Flags rows

A complete inventory with a suspicious (or flag) column set to yes on what matters. Those rows reach the Findings section of the report and findings.csv.

Context

Evidence with no verdict: timelines, channel dumps, inventories. Many feed another parser or the lateral-movement graph.
