Map of the tool

Artifact-Engine

DFIR triage from acquisition to report. Artifact-Engine verifies and extracts each acquisition, identifies every machine in it, runs the parsers that apply and writes a SQLite database, an Excel workbook and a report per machine. It runs on Windows; the evidence can come from Windows or Linux.

One run

Six phases, in this order

phase 0

Integrity

SHA-256 of every original, recorded in traces.txt before anything is opened. Append-only.

phase 1

Extraction

Nested zip, tar and 7z archives, in parallel and never destructively. An acquisition that does not extract completely is marked partial and changes the exit code.

phase 2

Detection

Profiles identify each machine (KAPE, UAC, Velociraptor, loose folders), its volumes and its VSS snapshots.

phase 3

Parsing

All parsers in one pool, ordered by depends_on. A failure stops only that parser; results from an earlier run are reused as cached.

phase 4

Consolidation

<machine>.db, .xlsx and report.txt (log coverage and findings), plus the case's run-summary.

phase 5

Lateral movement

Logons correlated across machines: lateral_movement.csv and an offline interactive graph with pivot chains.

What comes in

Acquisitions it recognises

windows_kape

KAPE / CyLR

A Windows acquisition collected with KAPE or CyLR, recognised by a volume root holding $MFT or Windows/System32; the host name comes from the acquisition name.

linux_uac

UAC

A Linux acquisition collected with UAC, recognised by its uac.log.

windows_liveresponse

Velociraptor LiveResponse

Volatile state. Inside a KAPE acquisition it joins its host; on its own it becomes a separate machine with an -LR suffix. Recognised by the detector, not by a profile manifest.

evtx

Loose evtx[-label] folder

Windows event logs dropped loose in an evtx[-label] folder at the case root. The folder becomes a machine: EvtxECmd and hayabusa run over it, results go to its own .db and .xlsx, and its logons feed the lateral-movement graph.

weblogs

Loose weblogs[-label] folder

Web-server access logs dropped loose in a weblogs[-label] folder at the case root. The folder becomes a machine: the web parsers read every file in it and write to its own .db and .xlsx.

fortigate

Loose fortigate[-label] folder

A FortiGate/FortiOS log export (syslog or FortiAnalyzer CSV) dropped in a fortigate[-label] folder at the case root. The folder becomes a machine with a flagged firewall timeline in its own .db and .xlsx.

linux_memory

linux_memory

A Linux memory image (.raw, .mem, .vmem, .lime of 64 MiB or more; .dmp of 256 MiB or more) in the top two levels of the case, recognised by its kernel banner. A sibling <stem>_memory/ folder points to the image and is the machine; Volatility 3 runs one Linux plugin per parser with symbols from the public ISF index. The image is never moved or copied.

windows_memory

windows_memory

A Windows memory image (.raw, .mem, .vmem, .lime of 64 MiB or more; .dmp of 256 MiB or more) in the top two levels of the case, unless recognised as Linux. A sibling <stem>_memory/ folder points to the image and is the machine; Volatility 3 runs one plugin per parser, and the unit is renamed after the COMPUTERNAME it holds. The image is never moved or copied.

What comes out

The 200 parsers

One row per parser: what it reads, where its tables are written and what they hold. A table is named after the parser id; a parser that runs an external tool can write several.

Alerts

alert_*. Every row is a finding: a rule hit (Sigma, YARA, GTFOBins), a catalogue match (LOLBAS, LOLDrivers, LOLRMM) or a check that lists only what it caught. The description names the fields. Rows rated in level are listed in the report's Findings and findings.csv.
